# Instrucciones para agentes

Este repositorio contiene el ETL en C# y .NET 10 para Alma Analytics, Springshare LibCal y Elogim/MariaDB. La base de destino es PostgreSQL en Neon. La reportería se desarrolla en otro repositorio.

- Trabajar en consola y mantener la separación Domain, Application e Infrastructure. La solución activa contiene estos tres proyectos y Console. El host sin funciones se conserva fuera de la solución para la futura migración a Azure.
- Conservar la DLL y la referencia de TI en `lib/` y `docs/template-*`. La integración de observabilidad corporativa se dejó para otra etapa. Verificar compatibilidad Linux y acordar el collector OTLP con TI antes de integrarla.
- Mantener README como descripción breve. Compartir instrucciones de ejecución y validación en el chat. Usar este archivo para el contexto vigente y Git para el historial.
- Preferir cambios pequeños y reutilizar lo existente. Evitar dependencias, frameworks de pruebas y scripts de comprobación permanentes sin necesidad. Usar Context7 para documentación vigente de bibliotecas, APIs, CLI y servicios.
- Confirmar cambios coherentes y verificados con commits. Distinguir las pruebas del agente de las validaciones del usuario. Mantener el repositorio privado y excluir credenciales, datos personales y respuestas del origen de los logs y artefactos.
- El presupuesto es cero. Mantener Neon, GitHub Actions y Cloudflare en las cuotas gratuitas autorizadas. Functions y el eventual cambio de motor quedan diferidos.

## Operación

- Cloudflare dispara diariamente a las 22:07 de Lima mediante `7 3 * * *` UTC. El código conservado en `scripts/cloudflare-etl-trigger.mjs` registra la fecha D a partir del evento, comprueba que sigue dentro de la noche de Lima y llama a GitHub con `reference_date=D` y `source=all`. El Worker usa `GITHUB_DISPATCH_TOKEN` y solo necesita permiso Actions de escritura para este repositorio.
- `.github/workflows/etl-neon.yml` solo usa dispatch. El cron nativo de GitHub se descartó por retrasos de varias horas y variabilidad observada. Mantener un solo programador productivo.
- El job usa ubuntu-24.04, una compilación Release y pasos independientes para LibCal, Alma y Elogim. Si una fuente falla, intenta las demás y el job queda fallido. El grupo único de concurrencia encola las ejecuciones y evita solapar cargas.
- Secretos de GitHub: `ALMA_API_KEY`, `LIBCAL_CLIENT_ID`, `LIBCAL_CLIENT_SECRET`, `ELOGIM_CONNECTION_STRING` y `NEON_CONNECTION_STRING`. Ambas conexiones usan formato .NET. Elogim respeta el modo TLS explícito de la cadena y, en remoto, usa VerifyFull si no se especifica. Neon remoto usa VerifyFull. `ELOGIM_TABLE` es opcional y el origen predeterminado es `est_ezproxy`.
- Los comandos de consola `--load-alma`, `--load-elogim` y `--load-libcal` aceptan `--date YYYY-MM-DD` como D. `--source all` por sí solo únicamente calcula el plan. Las opciones `--inspect-*` y `--extract-*` sirven para diagnóstico sin escribir resultados. `--init-db` aplica el esquema base a instalaciones nuevas. El workflow diario no ejecuta DDL.
- Para recuperar Alma y Elogim, usar la fecha de referencia original D y la fuente correspondiente. LibCal solo consulta el día actual en Lima y protege el cambio de fecha. Si se omite la foto de un día, esta ruta no permite recuperarla después.

## Contratos de datos

- **Alma D−2.** API regional `api-na.hosted.exlibrisgroup.com`, carpeta `/shared/Universidad Continental 51UCCI_INST/Reports/API/`, reportes Loans y Renewals. Filtros prompted `"Loan Date"."Loan Date"` y `"Renewal Date"."Renewal Date"`. Se envía igualdad para un día, se usa el token inicial para continuar y se verifica la fecha de cada fila. Ante un fallo en paginación repetir la extracción completa. Column0 es auxiliar y se omite. Conservar el literal Uso interno y la medida renewals. El conteo de renovaciones se obtiene con SUM(renewals) y la medida no incluye autorrenovaciones. ITEM_LOAN_ID identifica un préstamo y puede aparecer en varias renovaciones.
- **Elogim D−1.** Seleccionar las cinco columnas autorizadas por intervalo semiabierto de medianoche a medianoche. `fecha_sesion` es DATETIME en hora local de Perú, sin convertir a UTC. `id_est` llega a Neon como `user_email`. `identificacion` es DNI o código y se conserva como texto, incluidos ceros iniciales. El CASE del origen transforma pdf, busqueda y sesion a Descarga, Búsqueda y Acceso. MariaDB tiene una PK `id` que el ETL no necesita extraer.
- **LibCal D.** Contrato en `docs/apis/libcal-v1.1.openapi.yml` y catálogo de 14 categorías en `src/PipelineEtl.Console/libcal.categories.json`. OAuth client credentials. Consultar `/space/bookings` por lid y cid, con `days=0`, paginación y flags de asistencia, formularios y estados. Incluir canceladas, tentativas y denegadas. Validar el solape con el día de uso en Lima y las fechas con offset.
- **LibCal, formularios.** Teléfono q25458. Correos de integrantes 2 y 3 en q25459 y q25460 solo para espacios grupales. Valores vacíos se guardan como NULL. Guardar como `booking_note` solo la nota interna no vacía más reciente, usando el orden de respuesta para desempatar. Conservar estado de reserva y asistencia como campos distintos. El correo canónico es `user_email`. Los campos de tiempo canónicos son `booking_starts_at` y `booking_ends_at`. Derivar fecha, mes, año y hora en reportería con la zona Lima y calcular duración por diferencia de instantes. No persistir el JSON ni derivar un identificador de usuario del correo.
- **PostgreSQL.** Las tablas son `etl.alma_loans`, `etl.alma_renewals`, `etl.elogim_sessions` y `etl.libcal_bookings`. Cada carga reemplaza un día por tabla con COPY, lock transaccional y un índice no único por `extraction_date`. Se conservan los registros que comparten valores e IDs. En LibCal se observaron `booking_id` compartidos por filas de la misma captura y registros repetidos entre capturas cuando cruzan medianoche. El esquema tiene un solo archivo `schema.sql`. Efectuar ajustes sobre bases existentes como una operación explícita y conservar los datos.
- **Estado de carga.** `etl.load_status` registra por `dataset` y `extraction_date` el último conteo confirmado y su hora `loaded_at`. Cero significa carga confirmada sin filas. Un fallo revierte la carga activa y conserva el lote anterior y su estado. Las tablas de datos no tienen `row_number` ni `loaded_at`.
